OBJETIVO: ANALISIS DE SEGURIDAD Y ARQUITECTURA DEL PROYECTO DERECHOS ART CONSULTAS

ESTADO GENERAL DEL PROYECTO:
EL SISTEMA UTILIZA UNA ARQUITECTURA MVC SIMPLE CON UN FRONT CONTROLLER (INDEX.PHP), PDO PARA LA BASE DE DATOS Y PHPMAILER PARA CORREOS. LA SEGURIDAD A NIVEL DE SERVIDOR (.HTACCESS) ES SOLIDA.

HALLAZGOS CRITICOS Y MEJORAS:

1. RIESGOS DE XSS (CROSS-SITE SCRIPTING) EN MENSAJES DE SESION:
   - UBICACION: SRC/VIEWS/INICIO.PHP Y SRC/VIEWS/GESTION.PHP.
   - DETALLE: SE ESTA USANDO ADDSLASHES() PARA PASAR VARIABLES DE PHP A BLOQUES DE SCRIPT JAVASCRIPT.
   - RIESGO: ADDSLASHES NO ES UN METODO SEGURO PARA PREVENIR INYECCIONES DE CODIGO EN ATRIBUTOS O SCRIPTS.
   - RECOMENDACION: REEMPLAZAR ADDSLASHES() POR JSON_ENCODE() PARA ASEGURAR QUE LOS MENSAJES NO PUEDAN EJECUTAR CODIGO MALICIOSO EN EL NAVEGADOR.

2. LOGICA DE ESTRUCTURA (DDL) DENTRO DE MODELOS:
   - UBICACION: SRC/MODELS/GESTIONMODEL.PHP (METODO ELIMINARCONSULTA).
   - DETALLE: EL MODELO INTENTA EJECUTAR UN "ALTER TABLE" PARA CREAR LA COLUMNA 'ELIMINADO' SI NO EXISTE.
   - PROBLEMA: ESTO ROMPE LA SEPARACION DE RESPONSABILIDADES. LOS MODELOS DEBEN GESTIONAR DATOS, NO LA ESTRUCTURA DE LAS TABLAS. ADEMAS, REQUIERE PERMISOS EXCESIVOS PARA EL USUARIO DE LA DB.
   - RECOMENDACION: MOVER ESTA LOGICA AL SCRIPT DE MIGRACION O INICIALIZACION (INICIALIZAR_DB.PHP).

3. DEPENDENCIA DE ID DE USUARIO HARDCODEADO:
   - UBICACION: AUTHCONTROLLER Y AUTHMODEL.
   - DETALLE: EL SISTEMA DE LOGIN Y CAMBIO DE CONTRASENA ESTA ATADO EXCLUSIVAMENTE AL USUARIO CON ID = 1.
   - RIESGO: SI EL ID 1 NO EXISTE O SE CAMBIA, EL ACCESO ADMINISTRATIVO SE BLOQUEA TOTALMENTE.
   - RECOMENDACION: BUSCAR AL USUARIO POR NOMBRE DE USUARIO O CORREO ELECTRONICO.

4. ARCHIVOS DE INICIALIZACION EN EL SERVIDOR:
   - UBICACION: PUBLIC_HTML/INICIALIZAR_DB.PHP.
   - DETALLE: EL ARCHIVO PERMITE RESETEAR TABLAS Y CREAR USUARIOS CON CREDENCIALES POR DEFECTO.
   - ESTADO: ESTA BLOQUEADO POR .HTACCESS, PERO SIGUE SIENDO UN RIESGO RESIDUAL.
   - RECOMENDACION: ELIMINAR EL ARCHIVO DEL SERVIDOR UNA VEZ QUE LA BASE DE DATOS ESTE CONFIGURADA.

PUNTOS FUERTES (MANTENER):
- PREVENCION DE INYECCION SQL: USO CONSISTENTE DE PDO Y SENTENCIAS PREPARADAS EN TODOS LOS MODELOS.
- CONFIGURACION DE APACHE (.HTACCESS): BLOQUEO EFECTIVO DE DIRECTORIOS SENSIBLES (SRC, CONFIG, VENDOR, .GIT).
- ESCAPE DE DATOS EN VISTAS: USO CORRECTO DE HTMLSPECIALCHARS() EN LA RENDERIZACION DE TABLAS.
- VALIDACION DE INPUTS: FILTRADO DE TIPOS DE DATOS (INT, FLOAT) Y USO DE EXPRESIONES REGULARES PARA TELEFONOS.

PROXIMOS PASOS RECOMENDADOS:
1. CAMBIAR ADDSLASHES POR JSON_ENCODE EN TODAS LAS VISTAS.
2. REFACTORIZAR EL MODELO PARA ELIMINAR SENTENCIAS ALTER TABLE.
3. IMPLEMENTAR UN SISTEMA DE LOGIN BASADO EN NOMBRE DE USUARIO.
